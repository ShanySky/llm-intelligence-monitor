# Blocking findings

1. **PriceService.changePrice — ignored_write_result.** `updateIfVersion` can return `false`, but the method still evicts the cache and enqueues an audit for `expectedVersion + 1`. A rejected write can therefore produce an audit for a version/price that was never accepted (or misattribute another writer's version). Check the result and publish work only for a successful update; make the unsuccessful attempt a conflict/no-op without an audit.

2. **PriceService.changePrice — transaction_visibility.** Cache eviction and queue publication run before the price transaction commits. A cache miss can read the old committed row after the eviction and repopulate the shared cache with a stale price, even after the new price commits; an in-flight miss can also repopulate after a simple post-commit eviction. Conversely, the queue can deliver an audit for a transaction that later rolls back. Coordinate cache population/invalidation with committed versions so older reads cannot overwrite an accepted version, and persist audit work atomically with the accepted price (for example, a transactional outbox), publishing it only after commit.

3. **AuditWorker.deliver — payload_snapshot.** The worker fetches the *current* product price while using the queued *earlier* version. If version 2 is accepted before version 1's work is delivered, it sends version 1 paired with version 2's price, permanently corrupting that version's audit. Store the accepted version's price in immutable audit work at write time (or read an immutable versioned history record), and send that snapshot rather than `repo.find`'s current value.

4. **AuditWorker.deliver — retry_idempotency.** A fresh UUID is used on every delivery attempt. If the sink accepts the first send but the worker retries after a timeout/crash, the sink sees a new key and records the same logical audit twice. Derive and reuse a stable business key from product ID and accepted version on every attempt.

5. **WebhookService.paid — business_identity_scope.** Both `findOrCreate` and `inventory.reserve` use the provider event ID as the fulfillment identity. Two distinct event IDs for the same order version pass the version guard, create separate fulfillments, and reserve inventory under different keys; a crash after the first reservation but before commit makes that duplication especially likely on a later event. Key the durable fulfillment and the external idempotency request by the same stable order/version business operation, with a uniqueness constraint, and reuse that key on recovery.

6. **WebhookService.paid — lost_update.** The version test and assignments to `OrderState` are not an atomic conditional transition. Concurrent deliveries for versions 1 and 2 can both read the old state, then commit version 2 followed by version 1, regressing the stored version/status and admitting stale work. Serialize per-order transitions or use a version-checked conditional update with conflict retries, ensuring older versions cannot overwrite newer committed state; coordinate fulfillment with the accepted transition.

7. **WebhookService.paid — external_effect_recovery.** `inventory.reserve` executes before the local transaction commits, and the only reservation key/completion record is written afterward in that transaction. If the process fails at `afterReserve`, inventory may retain a reservation with no committed local record. A newer version can then commit; when the older event is retried, the version guard skips it, leaving the earlier external reservation untracked rather than recovering or reconciling it. Persist a durable order/version reservation intent before the external call, and reconcile attempts after failures (including superseded versions), so accepted reservations are either represented by the intended fulfillment or explicitly compensated.

8. **ReservationMover.move / cancelPair — lock_order.** `move(A,B)` takes A then B while `cancelPair(A,B)` takes B then A. Concurrent calls can each hold one account lock and wait forever for the other. Acquire the two locks in ascending account-ID order in every pair operation (including both methods).
